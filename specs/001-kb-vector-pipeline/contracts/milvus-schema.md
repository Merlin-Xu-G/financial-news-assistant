## 字段定义

| 字段 | Milvus 类型 | 参数 | 可空 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `VARCHAR` | `max_length=128`, `is_primary=True` | 否 | 片段标识，见 `data-model.md` E3 |
| `vector` | `FLOAT_VECTOR` | `dim={EMBEDDING_DIM}` | 否 | 语义向量 |
| `symbol` | `VARCHAR` | `max_length=16` | 否 | 股票代码，**过滤字段** |
| `name` | `VARCHAR` | `max_length=64` | 是 | 公司名称 |
| `section` | `VARCHAR` | `max_length=64` | 否 | 章节名，**过滤字段** |
| `part` | `INT16` | — | 否 | 分片序号，≥ 1 |
| `parts` | `INT16` | — | 否 | 分片总数，≥ `part` |
| `text` | `VARCHAR` | `max_length=8192` | 否 | 片段正文（含上下文头） |
| `content_hash` | `VARCHAR` | `max_length=64` | 否 | 内容指纹（sha256），用于判断片段是否需要更新 |

**不包含** `chars` 字段——该值仅用于阶段二统计，不参与过滤或展示（见 `data-model.md` E4 字段裁剪说明）。

**`content_hash` 的取值**：对 `symbol` / `name` / `section` / `part` / `parts` / `text` 六个字段做规范化 JSON 序列化后取 sha256，保证「内容变了哈希必变」。

## 集合生命周期

```text
                    集合存在？
                   ╱          ╲
                否             是
                 │              │
                 ▼              ▼
           创建集合          校验 vector 字段维度
           + 建索引              │
                 │        与 EMBEDDING_DIM 一致？
                 │          ╱        ╲
                 │        是          否
                 │         │            │
                 └─────────┴────────────┴──→ 报错退出（码 2）
                                             禁止删除或重建
```

**硬性规则**：

- 集合**已存在时绝不删除或重建**（FR-021）
- 维度不匹配时**明确报错并退出码 2**，不得尝试自动修复
- 集合不存在时自动创建并建立索引（无需用户手动建表）

## 写入语义

### 幂等键

`id` 字段作为唯一键。相同 `id` 重复写入视为同一条记录。

### 写入操作

使用 Milvus 的 `upsert` 语义：

| 场景 | 结果 |
| --- | --- |
| `id` 不存在 | 新增记录 |
| `id` 已存在，内容相同 | 记录不变，总数不变（FR-015、SC-004） |
| `id` 已存在，内容变更 | 记录更新为最新内容，总数不变（FR-016） |

### 断点续传与内容更新

每批写入前，以该批的 `id` 集合查询向量库，同时取回 `content_hash`：

```text
查询: id in [本批 id 列表]  →  output_fields=["id", "content_hash"]

id 不存在              →  走「嵌入 → upsert」
id 存在且哈希一致       →  跳过，不调用嵌入接口
id 存在但哈希不一致     →  走「嵌入 → upsert」（内容已变，需更新）
```

**理由**：嵌入接口按调用计费，跳过未变更片段避免重复计费（`research.md` R7）。

**为什么不能只用 `id` 判断**：仅凭 `id` 是否存在无法区分「内容未变」与「内容已变」。
若一律跳过，内容更新后向量库会残留旧内容，违反 FR-016；
若一律重写，则失去跳过带来的成本节省。`content_hash` 是同时满足两者的最小代价。

### 批次策略

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 批大小 | 16 | 每批提交嵌入接口的片段数 |
| 批间限速 | 1.0 QPS | 沿用 `infoway_client.py` 的限速语义 |
| 单批重试 | 4 次 | 遇 429 指数退避 |
| 单批最终失败 | 记录后继续 | 不中断整体（FR-018） |

## 检索契约（本 feature 只定义，不实现）

下游检索工具必须遵循以下约定，本 feature 不提供检索接口。

```text
输入:  查询文本、可选的 symbol 过滤、可选的 section 过滤、top_k
输出:  按相似度降序的记录列表，每条含 id / symbol / name / section / part / parts / text
```

**硬性规则**：

- 过滤条件必须下推到 Milvus（利用 `INVERTED` 索引），不得在客户端二次过滤
- 返回结果必须携带完整来源元数据（宪法第 II 条）
- **禁止将返回的 `text` 中的数值作为精确数值来源**（宪法第 I 条）；数值必须走 `metrics.sqlite`

## 验收要点

| 契约点 | 验证方式 | 对应 spec |
| --- | --- | --- |
| 集合自动创建 | 空库执行 `index`，集合与索引自动出现 | FR-014 |
| 维度校验 | 用错误的 `EMBEDDING_DIM` 执行，退出码 2 且集合未被破坏 | FR-021 |
| 幂等写入 | 同一批数据连续入库两次，记录总数不变 | FR-015、SC-004 |
| 内容更新 | 修改片段文本后重新入库，记录数不变且内容为新值 | FR-016 |
| 过滤有效性 | 按 `symbol` 过滤检索，结果全部属于该股票 | FR-017、SC-004 |
| 断点续传 | 中断后重跑，已入库片段不再触发嵌入调用 | FR-024 |
