# Feature Specification: 知识库向量流水线

**Feature Branch**: `001-kb-vector-pipeline`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "我们先把存文件，拆向量，进mvils的架构写好，注意代码简洁度，逻辑清晰"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从原始采集数据生成结构化知识文档 (Priority: P1)

开发者已经采集到一批股票的原始数据，需要把这些散落在多个接口文件里的信息，整理成每只股票一份、可读且结构稳定的知识文档，同时把其中的精确数值抽出来单独存成结构化记录。

**Why this priority**: 这是整条流水线的源头。没有知识文档，后续的片段切分和向量入库都无从谈起。它也直接决定了最终能被检索到的内容质量。

**Independent Test**: 取一只已采集完整原始数据的股票，执行文档生成，检查产出的知识文档是否包含全部有数据来源的章节、数值是否与原始数据一致、重复执行是否产生相同结果。

**Acceptance Scenarios**:

1. **Given** 一只股票的原始数据完整，**When** 执行文档生成，**Then** 产出一份按固定章节组织的知识文档，且全部有数据的章节都被包含
2. **Given** 一只股票缺少某类原始数据，**When** 执行文档生成，**Then** 缺失信息对应的章节被跳过，文档中不出现空章节或占位符
3. **Given** 已生成过文档的股票，**When** 再次执行文档生成，**Then** 产出内容与首次完全一致，且不产生重复记录
4. **Given** 一只股票的原始数据中包含精确数值指标，**When** 执行文档生成，**Then** 这些数值同时出现在结构化记录中，并带有指标名、数值、单位、期间、来源标识

---

### User Story 2 - 把知识文档切成可检索片段 (Priority: P2)

知识文档整篇太长，不适合直接作为检索单元。开发者需要把它切成一个个语义完整的片段，每个片段自带出处信息，脱离原文档也能看懂，并且能按股票和章节精确定位。

**Why this priority**: 片段是检索的最小单元，片段质量直接决定检索结果的可用性。切分不当会导致语义割裂，检索出来的内容答非所问。

**Independent Test**: 取一份知识文档执行切分，检查每个片段是否语义完整、是否携带出处元数据、超长章节是否正确分片且保留重叠、重复执行结果是否一致。

**Acceptance Scenarios**:

1. **Given** 一份知识文档，**When** 执行切分，**Then** 产出若干片段，每个片段携带唯一标识、股票代码、股票名称、章节名、分片序号
2. **Given** 一个章节内容超过片段长度上限，**When** 执行切分，**Then** 该章节被拆成多个片段，相邻片段在切口处保留重叠内容，且不在句子中间断开
3. **Given** 任意一个片段，**When** 单独阅读该片段正文，**Then** 不依赖原文档即可判断出它属于哪只股票的哪个章节
4. **Given** 已切分过的文档，**When** 再次执行切分，**Then** 产出片段集合与首次完全一致
5. **Given** 片段长度上限与重叠长度参数，**When** 调整参数重新切分，**Then** 产出片段的长度分布随之改变且仍满足语义完整要求

---

### User Story 3 - 把片段写入向量库并可供检索 (Priority: P3)

开发者需要把切好的片段写入向量库，使它们能被语义检索到，并且支持按股票代码、章节等条件先过滤再检索，避免跨股票召回噪声。

**Why this priority**: 这是流水线的终点，也是整条链路价值的兑现点。前两个阶段产出再好的数据，不入库就等于零。

**Independent Test**: 取一批片段写入向量库，用语义查询验证能命中预期片段；重复写入验证记录数不增长；按股票代码过滤验证只返回目标股票的结果。

**Acceptance Scenarios**:

1. **Given** 一批已切分的片段，**When** 执行写入，**Then** 每个片段在向量库中生成一条带向量表示与元数据的记录
2. **Given** 已写入向量库的片段，**When** 再次执行写入，**Then** 向量库记录总数不变，不产生重复记录
3. **Given** 某片段内容发生变更，**When** 重新写入该片段，**Then** 向量库中对应记录被更新为最新内容，记录总数不变
4. **Given** 向量库中已有多个股票的数据，**When** 按指定股票代码过滤后执行语义检索，**Then** 返回结果全部属于该股票
5. **Given** 写入过程中某一批次失败，**When** 该批次结束后，**Then** 整体流程继续处理后续批次，失败批次被完整记录且可单独重试
6. **Given** 向量库不可达，**When** 执行写入，**Then** 系统明确报告连接失败并保持数据可重试，不静默丢弃任何片段

---

### Edge Cases

- 某只股票的原始数据只有部分接口成功采集时，文档只包含成功部分，不报错也不留空章节
- 文档的某个章节只有标题没有正文时，该章节不产出片段
- 单个句子长度就超过片段长度上限时，按上限硬切并保证不产生空片段
- 结构化数值缺失单位或期间信息时，记录保留原始值并标注来源，不臆造单位
- 股票名称缺失时，片段上下文头退化为仅含股票代码，不阻断流程
- 同一股票代码在不同数据源出现重复记录时，以标识唯一性为准，重复写入被识别为同一记录
- 向量库中已存在同名集合时，写入流程复用而非重建，避免误删已有数据
- 全流程中断后重跑，已完成的部分不重复处理，未完成的部分从中断点继续

## Requirements *(mandatory)*

### Functional Requirements

**阶段一：知识文档生成**

- **FR-001**: 系统 MUST 能从单只股票的原始采集数据生成一份结构化知识文档
- **FR-002**: 知识文档 MUST 按固定章节组织，章节集合稳定可枚举，同类信息在每份文档中位于同名章节
- **FR-003**: 系统 MUST 同时产出结构化数值记录，每条记录包含指标名、数值、单位、期间、来源标识
- **FR-004**: 原始数据缺失某类信息时，系统 MUST 跳过对应章节，不得输出空章节、占位符，也不得臆造或推断内容
- **FR-005**: 同一输入重复执行文档生成 MUST 产生完全相同的输出

**阶段二：片段切分**

- **FR-006**: 系统 MUST 将知识文档切分为适合独立向量化的片段
- **FR-007**: 每个片段 MUST 携带全局唯一且稳定的标识，标识由「股票代码 + 章节 + 分片序号」确定性生成
- **FR-008**: 每个片段 MUST 携带可过滤的结构化元数据，至少包含股票代码、股票名称、章节名、分片序号
- **FR-009**: 片段正文 MUST 自带上下文头（股票名称 + 股票代码 + 章节名），保证脱离原文档仍可理解
- **FR-010**: 切分 MUST 在语义边界（句子）处进行，禁止在句子中间硬截断
- **FR-011**: 超长章节 MUST 被拆为多个片段，相邻片段在切口处保留重叠内容
- **FR-012**: 片段长度上限与重叠长度 MUST 可配置，且提供合理默认值
- **FR-013**: 同一输入重复执行切分 MUST 产生完全相同的片段集合

**阶段三：向量库写入**

- **FR-014**: 系统 MUST 为每个片段生成向量表示并写入向量库
- **FR-015**: 写入 MUST 幂等，同一片段重复写入不得产生重复记录
- **FR-016**: 片段内容变更后重新写入 MUST 更新已有记录，而非新增记录
- **FR-017**: 向量库 MUST 支持按股票代码与章节进行标量过滤后再执行语义检索
- **FR-018**: 写入 MUST 分批进行，单批失败 MUST NOT 中断整体流程，失败项 MUST 被完整记录且可单独重试
- **FR-019**: 系统 MUST 报告写入统计（成功数、跳过数、失败数）与耗时
- **FR-020**: 向量库不可达时，系统 MUST 明确报告失败并保持数据可重试，不得静默丢弃片段
- **FR-021**: 系统 MUST NOT 在写入时删除或重建向量库中已存在的其他数据

**跨阶段**

- **FR-022**: 三个阶段 MUST 均可独立执行，也可串联执行
- **FR-023**: 阶段之间 MUST 通过文件系统产物解耦，任一阶段可脱离上下游单独重跑
- **FR-024**: 全流程 MUST 支持断点续传，已完成的输入不重复处理
- **FR-025**: 每个阶段 MUST 输出可读的执行摘要，包含处理数、跳过数、失败数与耗时
- **FR-026**: 执行摘要 MUST 足以定位中断位置，使重跑能从断点继续
- **FR-027**: 所有中间产物 MUST 以原子方式写入，避免中断产生半截文件

### Key Entities

- **知识文档**：一只股票一份，按固定章节组织的可读文本。是片段切分的输入，也是人工核对数据正确性的依据。
- **知识片段**：检索的最小单元。含稳定标识、可过滤元数据、自带上下文的正文。是向量库记录的内容来源。
- **结构化数值记录**：从原始数据抽取的精确指标。含指标名、数值、单位、期间、来源标识。与文本分离存储，用于回答精确数值类问题。
- **向量库记录**：片段在向量库中的表示。含向量、元数据、原文，以片段标识作为唯一键。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 处理一只有完整原始数据的股票后，其知识文档包含全部有数据来源的章节，章节零遗漏
- **SC-002**: 任意片段脱离原文档后仍可独立理解，能判断出所属股票与章节
- **SC-003**: 任一阶段中断后重跑，已完成的输入不被重复处理，最终产物与一次性跑完完全一致
- **SC-004**: 同一批输入连续执行两遍完整流程，向量库记录总数保持不变
- **SC-005**: 写入完成后，按股票代码过滤的语义检索在 1 秒内返回结果
- **SC-006**: 处理单只股票的完整流程（文档生成 → 片段切分 → 写入向量库）在 10 秒内完成
- **SC-007**: 单批写入失败不影响其余批次的处理，失败项可从执行摘要中完整还原

## Assumptions

- 复用已有的原始采集产物作为输入，本 feature 不涉及重新采集
- 向量库为已部署的单机实例，通过标准客户端接入
- 向量表示由流水线生成，生成方式在技术方案阶段确定
- 目标市场为 A 股，股票代码格式为「6 位数字 + 交易所后缀」（如 `000001.SZ`）
- 本 feature 范围止于「数据已入库且可被语义检索」，面向 Agent 的检索工具封装属于后续 feature
- 精确数值的权威来源是结构化数值记录，文本片段仅用于定性描述，不得作为数值来源
- 原始数据的字段结构以现有采集产物的实际结构为准，不假设上游会变更格式
- 实现须遵守项目宪法，尤其第 IV 条「代码简洁」（禁止预防性抽象、禁止死代码、禁止吞异常、依赖最小化）
