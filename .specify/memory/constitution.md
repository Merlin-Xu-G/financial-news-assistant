# financialAgent Constitution

## Core Principles

### I. 数据不可信（NON-NEGOTIABLE）

任何金融数值都不得由 LLM 生成、推断或改写。

- 所有数值必须来自结构化查询（metrics.sqlite 或 Milvus 标量字段），禁止用向量检索结果作为数值来源
- 检索到的原文必须原样引用，禁止"约等于""大概是"式改写
- 数据缺失时必须显式输出「无数据」，禁止用估算值、行业均值或历史值填充
- 任何工具返回的数值必须携带来源标识（symbol + 指标名 + 期间）

理由：金融场景下错误数值的代价远高于"答不出来"。

### II. 可追溯

每个事实性结论都必须能回溯到原始数据。

- 输出必须标注来源：股票代码、章节、数据时间
- 检索片段必须保留原始 chunk id（格式 `{symbol}::{section}`）
- 禁止输出无法溯源到具体数据条目的结论
- 数据管道每一层（raw → text → chunks → 向量库）必须可反查上游

### III. 合规免责

- 所有输出必须包含风险提示
- 禁止给出买卖建议、目标价预测、仓位建议
- 禁止使用「必涨」「稳赚」「抄底」等诱导性表述
- 分析必须同时呈现正面与风险因素，禁止单边论述

### IV. 代码简洁（NON-NEGOTIABLE）

YAGNI 优先。不写当前 spec 未要求的东西。

- **禁止预防性抽象**：重复出现三次之前不得提取公共函数/基类/配置项
- **禁止死代码**：不提交注释掉的代码块、未使用的导入、变量、参数、函数
- **单一职责**：一个函数只做一件事；嵌套深度不超过 3 层
- **命名自解释**：命名必须能表达意图，禁止用注释弥补烂命名
- **禁止吞异常**：不得出现裸 `except:` 或 `except Exception: pass`；捕获必须处理或显式上抛
- **依赖最小化**：新增第三方依赖必须在 plan 中论证理由并登记 requirements.txt；标准库能解决的不用第三方
- **显式优于隐式**：禁止魔法数字、魔法字符串；常量必须具名
- **不留 TODO 债**：TODO 必须关联到 spec 中的任务条目，否则不写

理由：简洁是唯一能在长期维护中持续降低成本的特性。

### V. 规范驱动

- 所有功能必须先经 `/speckit.specify` → `/speckit.plan` → `/speckit.tasks`，禁止跳过流程直接改代码
- 任何代码变更必须能对应到 spec 中的需求条目
- spec 变更必须同步更新 plan 与 tasks，禁止产物之间不一致

### VI. 采集克制与可恢复

- 严格限速，默认 qps ≤ 1；遇到 429 必须退避重试，禁止提高并发硬闯
- 断点续传：任何中断后重跑必须能自动接续，不重复拉取
- 失败分级：永久失败（404/505/508）落 `skip/`，临时失败（网络/429）记录后可重试
- 稳定性优先于速度：禁止为缩短耗时牺牲限速或错误处理

## 技术约束

- Python 3.12+，全量类型注解，文件头 `from __future__ import annotations`
- 脚本形态统一：`argparse` 解析参数 + `main()` 返回退出码 + `raise SystemExit(main())`
- 依赖白名单：`requests`（当前唯一第三方依赖）
- 数据落盘：JSON / JSONL，写入必须原子（临时文件 + `os.replace`）
- 日志：标准 `logging`，同时输出控制台与文件
- 向量库：Milvus standalone，集合设计必须支持标量过滤（symbol / section）
- 密钥只放 `.env`，禁止硬编码，禁止提交

## 开发工作流

1. 每个 feature 建立独立 spec 目录，产物按序生成
2. `/speckit.plan` 阶段必须论证复杂度，简单方案优先
3. `/speckit.analyze` 必须验证产物与本章程一致
4. 实现完成后回写 spec 状态，保持文档与代码同步

## 治理

- 本章程优先于其他一切开发实践
- 修订必须记录变更理由并递增版本号
- 所有 spec、plan、代码审查必须验证与本章程的一致性
- 违反 NON-NEGOTIABLE 条款的变更不得合入
